# REVIEW.md — Defects found in the starter `app/main.py`

| # | Where (function / line) | What is wrong | How you'd notice it (test, input, or symptom) | How I fixed it |
|---|---|---|---|---|
| 1 | `list_employees` — `skip = page * page_size` | Off-by-one in pagination. Page 1 should skip 0 rows, but the code skips `1 * page_size`. Page 2 skips 40 instead of 20, etc. Every page returns the wrong slice. | Call `GET /employees?page=1&page_size=5` — the first 5 employees are skipped and you get employees 6-10. | Changed to `skip = (page - 1) * page_size`. |
| 2 | `list_employees` — `total = db.employees.count_documents({})` | `total` always counts the whole collection even when a `department` filter is applied. The spec says "total counts the filtered set, not the whole collection." | Filter by a department with 2 employees in a 10-employee DB. Response shows `total: 10` instead of `total: 2`. | Changed to `db.employees.count_documents(q)` after building the filter. |
| 3 | `list_employees` — no sort | The spec says "Sorted by `emp_code` ascending." The starter returns employees in insertion order (undefined). | Run with multiple employees; results vary between calls after concurrent inserts. | Added `.sort("emp_code", ASCENDING)`. |
| 4 | `punch_in` — `datetime.fromtimestamp(body.punched_at / 1000)` — naive datetime | Uses system-local timezone instead of UTC. On a server not in IST, the attendance date (`d`) will be wrong. Also, `datetime.now()` produces a naive datetime, so comparisons between naive and aware datetimes can raise `TypeError`. | On a UTC server: punch-in at 00:15 IST (18:45 UTC previous day) produces wrong date. | Used `datetime.fromtimestamp(..., tz=timezone.utc)` and `datetime.now(tz=timezone.utc)` everywhere. |
| 5 | `punch_in` — no 404 for unknown employee | `emp = db.employees.find_one(...)` is called but its result is never checked. If `emp` is `None`, the code crashes with `TypeError: 'NoneType' object is not subscriptable` when accessing `emp["shift_start"]`. | Send a punch-in for a nonexistent `emp_code`. The server returns 500 instead of 404. | Added `if not emp: raise HTTPException(404, ...)` immediately after the lookup. |
| 6 | `punch_in` — check-then-insert race condition | `find_one` + `insert_one` is not atomic. Two simultaneous requests for the same (emp_code, date) both pass the `find_one` check and both insert, creating duplicate records. | Hit the endpoint with two identical requests at the same time. Both return 201. | Removed the `find_one` guard entirely; rely on the unique compound index `(emp_code, date)` and catch `DuplicateKeyError`. |
| 7 | `compute_late_minutes` — wrong grace period logic | The code computes `minutes = int((punch_in - start).total_seconds() / 60)` and returns it when `> 10`. The spec (R2) says: late only if *strictly more than* 10:00 (600 seconds) after shift_start, and `late_minutes` = floor minutes since shift_start (not floor of the excess). Example: 09:40:01 → diff = 601 s → should return 10, not 0. The starter returns 0 for anything ≤ 10 minutes (correct boundary) but the integer division loses the "strictly > 10:00" requirement when the diff is exactly 600 s. | Punch in at exactly 09:40:00 (600 s late). Starter returns 0 ✓. Punch in at 09:40:01 (601 s late). Starter computes `int(601/60)=10` and returns it ✓. However, the "600 s" check in the starter is `> 10` (minutes), i.e. `> 600` seconds (since the division happened first), which is equivalent but fragile. More critically, R2 says `late_minutes` is elapsed since `shift_start`, not since `shift_start + 10`. The starter happens to do this correctly for the integer value, but the conditional `if minutes > 10` checks minutes-after-start, which means a punch-in at exactly 10 min is treated as not late (correct per spec). Hidden defect: if `punch_in` has sub-second precision it may compute incorrectly. | Rewrote to compare raw seconds to 600, truncating to seconds as required by R1 and using integer floor division correctly. |
| 8 | `compute_overtime` — wrong date for overnight shifts | `end = datetime.fromisoformat(date_str).replace(hour=h, minute=m, tzinfo=IST)` always places shift_end on the attendance date. For an overnight shift (shift_end < shift_start, e.g. 22:00-06:00) the shift_end clock time occurs the *next* calendar day, so the overtime comparison is 24 hours off. | Employee EMP0005 (shift 22:00-06:00) punches out at 06:40 on the 7th. `date_str` is "2026-07-06". The starter places shift_end at 06:00 on the 6th instead of the 7th, producing a negative delta and returning 0 instead of 40. | Rewrote `compute_overtime_minutes` to try both same-day and next-day candidates and pick the one that gives the correct non-negative delta. |
| 9 | `list_attendance` — loads entire collection into memory | `list(db.attendance_logs.find(q))` fetches all matching documents, then sorts and paginates in Python. On 100k records this is slow and memory-intensive. | Run with 100,000 records and no filters; the request times out or uses gigabytes of RAM. | Moved sort and skip/limit into the DB query (`.sort().skip().limit()`). Also call `count_documents(q)` separately instead of `len(docs)`. |
| 10 | `list_attendance` — no validation of `date_from > date_to` | The spec says `date_from > date_to` should return 422. The starter silently returns an empty set instead. | Send `date_from=2026-07-10&date_to=2026-07-01`. Returns 200 `{items:[]}` instead of 422. | Added an explicit check and `raise HTTPException(422, ...)`. |
| 11 | `health` | Returns `{"status": "ok"}` unconditionally without ever contacting MongoDB. The spec says it should return 503 if MongoDB is unavailable. | Kill MongoDB and hit `/health`. Returns 200 instead of 503. | Added `db.command("ping")` inside a try/except and returns 503 on failure. |
| 12 | `create_employee` — no unique-index enforcement at DB level | The code does a check-then-insert (`find_one` + `insert_one`), which is a race condition. Two concurrent creates for the same `emp_code` can both pass the check. | Send two simultaneous POST /employees with the same `emp_code`. Both return 201. | Created a unique index on `employees.emp_code` at startup and catch `DuplicateKeyError`. |
| 13 | `create_employee` — `created_at` stored as naive `datetime.now()` | Stored without timezone; MongoDB interprets naive datetimes as UTC, but any downstream code comparing with an aware datetime will fail. | Compare `created_at` with `datetime.now(tz=IST)`. Raises `TypeError`. | Changed to `datetime.now(tz=timezone.utc)`. |
| 14 | `punch_in` — attendance date computed incorrectly for overnight shifts | `d = ts.date().isoformat()` takes the naive local date of the punch-in. This is wrong in two ways: (a) it uses a naive datetime (bug 4), and (b) it ignores the R1 overnight-shift rule. | EMP0005 (22:00-06:00) punches in at 05:50 IST on the 7th. Should belong to date 2026-07-06 but the starter records date 2026-07-07. | Implemented `attendance_date()` that converts to IST and applies the overnight rule. |

## Things I looked at and decided were **not** defects

* **`compute_late_minutes` uses `int(...)`** — integer truncation is floor for positive numbers, which matches R2's "whole minutes (floor)". Not a defect.
* **Pydantic v2 `model_dump()`** — the starter correctly uses `model_dump()` (Pydantic v2 API) instead of the deprecated `.dict()`. Not a defect.
* **`body.status` not validated in `punch_in`** — a mild omission (the starter accepts any string) but handled cleanly by adding a Pydantic validator in my implementation.
